### ① 함수형 인터페이스와 람다

**함수형 인터페이스**: **추상 메서드가 딱 하나**인 인터페이스. 그래야 람다로 축약할 수 있다.

```java
// PART 3 MyRunner.java — 같은 일을 3가지 문법으로
args.getOptionNames().forEach(new Consumer<String>() {       // ① 익명 클래스
    @Override
    public void accept(String s) { System.out.println("arg name = " + s); }
});
args.getOptionNames().forEach(name -> System.out.println(name));   // ② 람다
args.getOptionNames().forEach(System.out::println);                // ③ 메서드 참조
```

**왜 축약이 가능한가**
- `Consumer<String>`의 추상 메서드는 `accept(String)` **하나뿐**이다
- 그러니 "어떤 메서드인지" 쓸 필요가 없다 → 이름과 `@Override`를 지우면 `(String s) -> { ... }`
- 파라미터 타입도 추론되고, 본문이 한 줄이면 중괄호와 `;`도 생략 → `name -> System.out.println(name)`
- 파라미터를 그대로 넘기기만 하면 **메서드 참조** → `System.out::println`

**주요 함수형 인터페이스 (`java.util.function`)**

| 인터페이스 | 추상 메서드 | 뜻 | 이 저장소에서 |
|---|---|---|---|
| `Consumer<T>` | `void accept(T)` | 받아서 소비 | `forEach`, `ifPresent` |
| `Supplier<T>` | `T get()` | 만들어서 공급 | `orElseThrow(() -> new ...)`, `orElseGet` |
| `Function<T,R>` | `R apply(T)` | 변환 | `map(...)` |
| `Predicate<T>` | `boolean test(T)` | 판정 | `filter(...)` |
| `Runnable` | `void run()` | 실행 | — |

🔗 PART 1 1-12절의 **인터페이스**가 기반이다. 람다는 결국 **인터페이스 구현체를 짧게 쓰는 문법**일 뿐이다.

**메서드 참조 4종**

| 형태 | 예 | 뜻 |
|---|---|---|
| `클래스::정적메서드` | `Integer::parseInt` | 정적 메서드 호출 |

| `클래스::인스턴스메서드` | `String::toUpperCase` | 받은 인자의 메서드 |
| **`클래스::new`** | `UserInfoUserDetails::new` | **생성자 참조** |

### ② Stream — 3단 구조

```java
// PART 4 StreamTest.java
List<String> result2 = names.stream()        // ① 생성   List<String> → Stream<String>
        .filter(name -> name.length() > 3)   // ② 중간   Stream → Stream
        .map(name -> name.toUpperCase())     //   중간
        .toList();                           // ③ 최종   Stream → List
```

| 단계 | 메서드 | 특징 |
|---|---|---|
| **생성** | `list.stream()`, `Arrays.stream(배열)`, `Stream.of(...)` | — |
| **중간 연산** | `filter` `map` `sorted` `distinct` `limit` `skip` | **Stream을 반환** → 체인 가능. **지연 실행** |
| **최종 연산** | `toList()` `collect()` `forEach` `count` `findFirst` `anyMatch` | **결과를 반환** → 여기서 실제 실행 |

**⚠️ 중간 연산은 최종 연산이 호출되기 전까지 실행되지 않는다(lazy).** `filter`만 쓰고 끝내면 아무 일도 일어나지 않는다.

**for문 대비 이점**
```java
// for 방식 — "어떻게" 할지를 쓴다 (명령형)
List<String> result1 = new ArrayList<>();
for (String name : names) {
    if (name.length() > 3) result1.add(name.toUpperCase());
}

// Stream 방식 — "무엇을" 할지를 쓴다 (선언형)
names.stream().filter(n -> n.length() > 3).map(String::toUpperCase).toList();
```
- 중간 변수(`result1`)와 `add` 호출이 사라진다
- **읽는 순서가 처리 순서와 같다** — 거르고 → 바꾸고 → 모은다
- ⚠️ 단점: 디버깅이 어렵고, 단순 반복은 for가 더 빠르다. **무조건 Stream이 좋은 것은 아니다**

**저장소에 등장한 Stream 3사례**

```java
// ① PART 3 UserInfoUserDetails — 문자열 → 권한 목록
Arrays.stream(userInfo.getRoles().split(","))
      .map(roleName -> new SimpleGrantedAuthority(roleName))
      .collect(Collectors.toList());

// ② PART 4 StudentService — 엔티티 목록 → DTO 목록
studentRepository.findAllWithStudentDetail()
      .stream()
      .map(StudentDTO.Response::fromEntity)
      .toList();

// ③ PART 4 DepartmentDTO — 연관 엔티티 목록 → 요약 DTO 목록
department.getStudents().stream()
      .map(StudentDTO.SimpleResponse::fromEntity)
      .toList();
```
**②③이 Stream의 실무 용법 1위다 — 목록 변환(Entity ↔ DTO).**

⚠️ **`toList()`와 `collect(Collectors.toList())`의 차이**
- `toList()` — **Java 16+**. 짧고, **불변(immutable) 리스트**를 반환
- `collect(Collectors.toList())` — 예전 방식. **가변 리스트**
- 저장소에 **둘 다 있다.** `collect`는 PART 3 Security 코드, `toList()`는 PART 4 코드. 반환 리스트를 수정할 일이 없으면 `toList()`가 낫다

### ③ Optional 정리 (PART 3 3-4절 확장)

| 메서드 | 동작 | 함수형 인터페이스 |
|---|---|---|
| `isPresent()` / `get()` | 있는지 확인 후 꺼냄 | — |
| `ifPresent(c)` | 있을 때만 실행 | `Consumer` |
| `map(f)` | 있으면 변환 | `Function` |
| `filter(p)` | 조건에 맞을 때만 유지 | `Predicate` |
| `orElse(v)` | 없으면 v (**항상 평가**) | — |
| `orElseGet(s)` | 없으면 s 실행 (**필요할 때만**) | `Supplier` |
| **`orElseThrow(s)`** | **없으면 예외** — 실무 표준 | `Supplier` |

```java
// PART 3 UserInfoUserDetailsService — map + orElseThrow 체인
optionalUserInfo.map(userInfo -> new UserInfoUserDetails(userInfo))
                .orElseThrow(() -> new UsernameNotFoundException("user not found " + username));
```

## B-2. [PART 2 보충] MyBatis 연관관계 매핑 ↔ JPA 대비

⚠️ **PART 2 2-8절에서 `StudentVO`가 `DeptVO dept`와 `List<CourseStatusVO> courseStatus`를 갖고 있다는 것만 짚고 "`resultMap`의 `<association>`/`<collection>`이 필요하다"고 넘어갔다.** PART 4에서 JPA로 같은 것을 했으니, 이제 정면 비교가 가능하다.

### 같은 관계, 두 가지 방법

**PART 2 — MyBatis (SpringFWXml)**
```java
public class StudentVO {
    private Long id;
    private Integer code;
    private String name;
    private DeptVO dept;                          // 1:1 (또는 N:1)
    private List<CourseStatusVO> courseStatus;    // 1:N
}
```
```xml
<!-- StudentMapper.xml — resultMap 을 직접 작성해야 한다 -->
<resultMap id="studentMap" type="Student">
    <id     property="id"   column="id"/>
    <result property="code" column="code"/>
    <result property="name" column="name"/>

    <association property="dept" javaType="Dept">          <!-- 1:1 / N:1 -->
        <id     property="id"   column="dept_id"/>
        <result property="name" column="dept_name"/>
    </association>

    <collection property="courseStatus" ofType="CourseStatus">  <!-- 1:N -->
        <id     property="id"    column="cs_id"/>
        <result property="score" column="score"/>
    </collection>
</resultMap>

<select id="selectStudentCourseStatus" resultMap="studentMap">
    SELECT s.*, d.name AS dept_name, cs.score
    FROM student s
      LEFT JOIN dept d ON s.dept_id = d.id
      LEFT JOIN course_status cs ON cs.student_id = s.id
</select>
```

**PART 4 — JPA (1toN)**
```java
@Entity
public class Student {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")           // N:1
    private Department department;

    @OneToOne(fetch = FetchType.LAZY, mappedBy = "student", cascade = CascadeType.ALL)
    private StudentDetail studentDetail;          // 1:1
}
```
```java
// SQL 을 안 써도 되고, 필요하면 JPQL 로
@Query("SELECT s FROM Student s LEFT JOIN FETCH s.studentDetail LEFT JOIN FETCH s.department")
List<Student> findAllWith(...);
```

### 정면 대조표

| 항목 | MyBatis | JPA |
|---|---|---|
| 관계 선언 | **XML `resultMap`** | **엔티티 어노테이션** |
| 1:1 / N:1 | `<association>` | `@OneToOne` / `@ManyToOne` |
| 1:N | `<collection>` | `@OneToMany` |
| 컬럼 매핑 | `column="..."` 직접 | 이름 규칙 자동 (`@Column`으로 조정) |
| SQL | **직접 작성** | **자동 생성** (필요 시 JPQL) |
| 조인 시점 | SQL에 쓴 대로 | **fetch 전략으로 결정** |
| 지연 로딩 | 설정 필요(`fetchType="lazy"`) | **기본 지원** |
| N+1 | 발생 가능(중첩 select 방식) | 발생 가능 → **fetch join** |
| 변경 감지 | **없음** — UPDATE SQL 직접 | **있음** (Dirty Checking) |
| 연관관계 주인 | 개념 없음 (SQL이 다 함) | **핵심 개념** |
| DB 종속성 | SQL이 DB에 종속 | **Dialect가 흡수** |
| 복잡 쿼리 | **유리** (SQL 그대로) | 불리 (JPQL 한계 → QueryDSL/네이티브) |
| 학습 곡선 | 낮음 | **높음** |

**⚠️ 어느 쪽이 좋은가 — 실무 기준**
- **JPA**: CRUD가 단순하고 도메인 모델이 명확한 서비스. 변경 감지·영속성 컨텍스트가 큰 이득
- **MyBatis**: 통계·리포팅처럼 **복잡한 조인과 튜닝이 필요한** 영역
- **한국 실무에서는 둘을 함께 쓰는 경우가 많다.** JPA로 CRUD, MyBatis로 복잡 조회.
- 🔗 리포트가 MyBatis를 "새 패러다임을 익힐 부담 없이 익숙한 SQL을 쓴다"고 소개한 이유가 이 표에서 드러난다.

### `CourseStatusVO`가 보여주는 것 — N:M의 정석

PART 2의 `CourseStatusVO(StudentVO, CourseVO, score)` 구조는 사실 **N:M을 중간 엔티티로 푼 것**이다.

```
Student  ──< CourseStatus >──  Course
              (score)
```
JPA로 옮기면:
```java
@Entity
public class CourseStatus {
    @Id @GeneratedValue private Long id;
    @ManyToOne(fetch = LAZY) @JoinColumn(name="student_id") private Student student;
    @ManyToOne(fetch = LAZY) @JoinColumn(name="course_id")  private Course course;
    private Integer score;                      // ★ 중간 테이블에만 있는 컬럼
}
```
🔗 **4-3절에서 "`@ManyToMany`는 실무에서 안 쓰고 중간 엔티티를 만든다"고 한 것의 실물 예시가 이미 PART 2에 있었다.** `score`라는 추가 컬럼 때문에 `@ManyToMany`로는 표현할 수 없다.

```
VM arguments      : -Dfoo   → args.containsOption("foo") == false  ⚠️ 시스템 프로퍼티라 안 잡힘
```
`-Dfoo`는 `System.getProperty("foo")` 또는 `environment.getProperty("foo")`로 읽어야 한다.

**로그 레벨 / devtools**
```
--debug     일부 핵심 라이브러리만 디버깅
--trace     전부 디버깅
logging.file.path=logs               → logs/spring.log 생성
logging.level.패키지명=debug
spring.devtools.restart.enabled=false   → 자동 재시작 끄기
```
`logback-spring.xml`로 Logback 상세 설정 가능:
```xml
<configuration>
    <include resource="org/springframework/boot/logging/logback/base.xml"/>
    <logger name="com.basic.boot" level="DEBUG"/>
</configuration>
```

### ④ 한글 인코딩 설정 (3.12절)

```properties
spring.http.encoding.charset=UTF-8
spring.http.encoding.enabled=true
spring.http.encoding.force=true
```
⚠️ **Spring Boot 2.1+부터 이 키는 `server.servlet.encoding.*`으로 바뀌었다.** 리포트는 구버전 기준. Boot 3에서는:
```properties
server.servlet.encoding.charset=UTF-8
server.servlet.encoding.force=true
```
사실 **기본값이 이미 UTF-8**이라 보통 설정할 필요가 없다. 🔗 PART 2에서 `web.xml`에 `CharacterEncodingFilter`를 직접 등록하던 것(그리고 `*.do`에만 걸어 REST 요청이 빠지던 버그)과 대비하면, 자동 설정이 무엇을 해결했는지 명확하다.

### ⑤ 프록시로 동작하는 것들 — 최종 목록 (3-10절 갱신)

PART 4에서 두 개가 추가되었다.

| 기능 | 어노테이션/타입 | 프록시를 만드는 주체 |
|---|---|---|
| AOP | `@Aspect` | Spring AOP |
| 트랜잭션 | `@Transactional` | Spring TX |
| 메서드 보안 | `@PreAuthorize` | Spring Security |
| MyBatis Mapper | `@Mapper` 인터페이스 | MyBatis-Spring |
| `@Configuration` | `@Bean` 메서드 | CGLIB |
| **JPA Repository** | `JpaRepository` 인터페이스 | **Spring Data JPA** |
| **Projection** | `DepartmentSummary` 인터페이스 | **Spring Data JPA** |
| **지연 로딩** | `@ManyToOne(fetch=LAZY)` 필드 | **Hibernate** |

**⚠️ 마지막 항목이 중요하다.** LAZY 필드에는 실제 엔티티가 아니라 **프록시 객체**가 들어 있다. 그래서:
- `student.getDepartment()`는 프록시를 반환한다 (쿼리 안 나감)
- `student.getDepartment().getName()`을 호출하는 순간 **초기화 쿼리**가 나간다
- 트랜잭션 밖이면 `LazyInitializationException`
- `instanceof` 비교나 `==` 비교가 예상과 다르게 동작할 수 있다

**"Spring/JPA에서 뭔가 이상하게 동작하면 프록시를 의심하라"** — 이것이 세 파트를 관통하는 마지막 교훈이다.
